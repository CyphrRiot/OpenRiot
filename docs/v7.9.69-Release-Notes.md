## Release Overview

Backing up the whole system to a bootable mirror used to freeze
the machine. It doesn't anymore. The drive manager gains a
second clone path that reads the raw filesystem sequentially
instead of walking 3.2TB of inodes, the swap that turned out to
be the murderer is taken out of the equation, the target is
checked and repaired before it's used, and the cancel key
finally, actually, cancels.

**Total changes: a sequential `dump | restore` clone, swap
discipline, a pre-mount `fsck`, a working cancel, and a
progress bar that moves.**

---

## 📦 The Sequential Clone

`dump 0af - /dev/rsd1a | (cd /mnt/backup && restore -rf -)`

**The Problem:** The only clone path was `rsync`. rsync walks
the tree one inode at a time — millions of random seeks through
the softraid crypto layer. Sequential reads are cheap; random
reads are not. The crypto pipeline backs up, the disk stops
answering, the machine locks, the force-reboot arrives, and you
spend the morning in `fsck`.

**The Fix:** A second option under **Full Backup** — *Clone to
/mnt/backup (dump | restore)*. `dump` reads the raw filesystem
cylinder-group by cylinder-group, in order, and pipes the stream
to `restore`, which writes the actual files into the target.
Same mirror as rsync. Sequential I/O instead of a random storm.

`rsync` stays for incremental runs — and it got harder to hurt
you: `nice -n 20`, `--delete-delay`, `--prune-empty-dirs`, and a
lower `--bwlimit`.

---

## 🔒 The Swap Was the Murderer

**The Problem:** Root, home, **and swap** all lived on one
softraid crypto volume. Under memory pressure the kernel paged
to swap — on the same encrypted disk rsync was already
saturating — and the crypto layer deadlocked on itself. `nice`
and `--bwlimit` only delayed it.

**The Fix:** The clone disables swap before it starts and
restores it when it's done, on every exit path — success,
failure, or cancel. Without swap on the same device, the
feedback loop has nowhere to form. There's no `dmesg` for this.
There is no error message. There is just a machine that doesn't
freeze.

---

## 🧹 The Filesystem Was Not Clean

**The Problem:** After a force-reboot the backup disk came back
dirty — `WARNING: R/W mount of /mnt/backup denied. Filesystem
is not clean - run fsck` — and the clone would run against a
filesystem that refused to mount.

**The Fix:** Before cloning, if `/mnt/backup` isn't already up,
the machine runs `fsck -y /dev/sd3a`, then mounts it. If it's
already mounted, `fsck` is skipped — a clean reboot isn't
punished with an unnecessary check.

---

## ⏹️ ESC Means Stop

**The Problem:** Pressing ESC set a flag and changed the message
to *cancelled*. It never touched the process. `dump` forks a
small army of children; `restore` holds the mount. The TUI said
"cancelled" while the disk kept grinding, and `umount` came back
`Device busy`.

**The Fix:** A watcher kills the whole tree — `dump`, `restore`,
`rsync` — the instant the flag is set. ESC means the machine
stops. `umount` means `umount`.

---

## 📊 A Bar That Tells the Truth

**The Problem:** The progress bar sat at `0.0%` forever. `dump`
only reports its own percentage when it receives `SIGINFO`, which
nothing was sending; `restore`'s per-file chatter churned the
header; the number measured the root partition against a 3.4TB
total so it barely moved; and the sweep animation only re-ticked
on the *other* progress screen, so it froze after one frame. A
cancel with no error message dereferenced a nil and panicked.

**The Fix:** Progress is measured from the target's own growth
against the partition being written, **per partition** — root
climbs 0→100%, then home climbs 0→100%. The sweep animates on
the clone screen too. The header keeps only the `DUMP:` lines,
so it reads `dumping (Pass IV) [regular files]` instead of
restore soup. And the cancel path no longer panics on a nil.
