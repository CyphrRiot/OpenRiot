## Release Overview

The machine already learned to copy itself by reading straight
through instead of walking inodes one at a time. This release
takes the last middleman out. A third **Full Backup** path writes
the raw partition to a single flat file, one pipe per partition,
so the file never has to be a filesystem and the encrypted queue
is never asked to hold two things at once. The progress bar stops
guessing where it is. And the machine stops running three
frequency governors at once.

**Total changes: a dump-to-file backup path, progress read from
the source, and one clock instead of three.**

---

## 📄 Dump to File

`dump 0af - /dev/rsd1a | pv > /mnt/backup/root.dump`

**The Problem:** The sequential clone fixed the I/O storm, but it
still restored a filesystem onto the target, one entry at a time,
and it still ran the whole thing back through the softraid crypto
queue on the way out. Two systems, one disk, one pipe. Under
enough weight it can still stall.

**The Fix:** A third entry under **Full Backup** — *Dump to file
/mnt/backup (dump → root.dump + home.dump)*. `dump` reads the raw
filesystem and writes it to one flat file, `root.dump` then
`home.dump`. No `restore`, no second filesystem, no queue
contention: one stream from the encrypted disk to a file on the
backup drive. To bring it back: `cd /mnt/backup && doas restore
-rf root.dump`.

---

## 📊 A Bar That Reads the Source

**The Problem:** Progress was guessed from how much the target
had grown against the source size. It moved, but it moved on a
guess, and the file path had almost nothing to measure at all.

**The Fix:** Progress now reads the percentage `dump` reports
itself, falling back to target growth only until the first report
arrives. The `dump | restore` path also gained `pv`, so the
stream is visible end to end. The bar tells you what the source
is doing, not what a disk happened to leave behind.

---

## 🕰️ One Clock

**The Problem:** Three things were steering the CPU. `apmd` ran
with `-A` to pick a frequency policy, `obsdfreqd` ran its own
scheduler, and OpenRiot's own display code set `hw.perfpolicy` at
runtime. Three clocks, one CPU, and they did not agree. A daemon
and a policy fighting over the same dial is a machine that cannot
decide how fast to think.

**The Fix:** `apmd` loses `-A` and keeps only its power events.
`obsdfreqd` is removed from `pkg_scripts` on install. Runtime
`hw.perfpolicy` is the single owner. Install also stops
duplicating `kern.maxfiles`: it deletes any stray line before it
writes the one it wants. One clock. The Feds would call competing
frequency daemons a "governance model" and invoice you for the
inefficiency. We call it one hand on the dial.
